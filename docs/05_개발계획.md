## 0. 계획 원칙

| # | 원칙 |
|---|---|
| P1 | **EPIC 경계는 "데이터 출처"로 나눈다: 없음 → 목업 → 실연동.** 각 경계에서 교체되는 의존성이 정확히 하나다 |
| P2 | EPIC 하나가 끝나면 **그것만으로 브라우저에서 결과를 확인할 수 있다** |
| P3 | STORY 하나에는 **한 가지 동작만** 담는다 |
| P4 | 모든 완료 조건은 **브라우저에서 눈으로 확인 가능한 문장**이다. "코드를 작성했다"는 완료 조건이 아니다 |
| P5 | `docs/03_FRD.md`에 없는 기능을 STORY로 만들지 않는다 |
| P6 | **테스트·보안 점검·배포는 세 EPIC 어디에도 들어가지 않는다.** 세 EPIC이 끝난 뒤 별도 단계(QA → 보안 검토 → 최종 점검)로 수행한다 |

### 0-1. EPIC 경계에서 교체되는 의존성

| 경계 | 이전 | 이후 | 교체되는 것 |
|---|---|---|---|
| EPIC 1 → 2 | 데이터 없음 (플레이스홀더 텍스트) | **`lib/mock/sample-itinerary.ts`** | 화면이 읽는 데이터 출처 1개 |
| EPIC 2 → 3 | `PLAN_SOURCE`가 `mock`으로 해석됨 (키 없음) | **`GEMINI_API_KEY` 투입 → `auto`가 `gemini`로 해석됨** | 라우트 핸들러가 부르는 생성기 1개 |

EPIC 2가 끝난 시점에 이미 `POST /api/plan`이 존재하고 `ItineraryPlan`을 반환한다. EPIC 3은 그 안의 생성기만 바꾼다. **화면 코드는 EPIC 2 이후 한 줄도 바뀌지 않는다.**

`PLAN_SOURCE`의 기본값이 `auto`이므로 경계 전환에 **설정 파일을 고칠 필요조차 없다** — 키를 넣으면 `gemini`, 빼면 `mock`이다.

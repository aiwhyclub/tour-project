# 01. 제품 요구사항 문서 (PRD) — 여행 큐레이션

| 항목 | 내용 |
|---|---|
| 제품명 | 여행 큐레이션 (Travel Curation) |
| 버전 | v1.0 |
| 작성일 | 2026-09-12 |
| 상태 | 확정 |

---

## 1. 문제

여행 계획을 세우는 사람은 **정보가 없어서가 아니라 너무 많아서** 막힌다.

블로그·커뮤니티·영상에 흩어진 정보를 모아 일자별로 배치하고, 예산을 가늠하고, 무엇을 챙길지 정하고, 비가 오면 어떻게 할지까지 정리하려면 몇 시간이 든다. 그 과정의 대부분은 "검색 → 읽기 → 취사선택 → 재배치"의 반복이며, 개인의 제약(예산, 동행 인원, 못 먹는 음식, 피하고 싶은 것)을 반영하려면 이 작업을 처음부터 다시 해야 한다.

기존 여행 서비스는 대부분 **예약·결제 전환**을 목적으로 설계되어, 아직 결정하지 않은 사람에게 필요한 "초안"을 주지 않는다. 사용자는 예약할 준비가 되기 전에 "그래서 대략 어떤 여행이 되는가"를 먼저 보고 싶어 한다.

**이 제품이 푸는 문제**: 여행 조건 몇 개를 입력하면, 검토·수정할 수 있는 **일정 초안 한 벌**을 즉시 받는다. 예약을 대신해주지 않고, 결정을 대신해주지도 않는다. 결정하기 위한 재료를 정돈해서 준다.

---

## 2. 대상 사용자

| 구분 | 설명 | 핵심 니즈 |
|---|---|---|
| **1차: 계획 착수 단계 여행자** | 목적지는 대충 정했지만 일정을 아직 짜지 않은 사람. 출발 2주~2개월 전 | "며칠을 어떻게 쓰면 되는지" 뼈대 |
| **2차: 제약 조건이 있는 여행자** | 부모님 동행, 아이 동반, 알레르기, 체력 제약, 예산 상한이 뚜렷한 사람 | 내 조건이 반영된 일정 |
| **3차: 계획을 싫어하는 여행자** | 계획 자체가 부담이라 미루는 사람 | 수정만 하면 되는 완성된 초안 |

**대상이 아닌 사용자**: 이미 일정을 확정하고 예약할 곳을 찾는 사람. 실시간 최저가를 비교하려는 사람. 현지에서 실시간 길찾기가 필요한 사람.

## 3. 사용자 시나리오

### 시나리오 A — 부모님과 제주 3일 (1차 + 2차 사용자)

> 40대 직장인이 부모님을 모시고 10월 초 제주도 2박 3일을 계획한다. 예산은 90만 원 정도를 생각하고 있고, 부모님 무릎이 좋지 않아 많이 걷는 코스는 피하고 싶다. 아버지는 고수를 못 드신다.

1. 여행지에 "제주도", 일정에 10/3–10/5, 인원에 성인 2 + 아동 1을 넣는다.
2. 예산 90만 원(총액), 스타일은 "힐링·자연·사진", 음식 취향은 "해산물·현지식", 못 먹는 재료에 "고수"를 적는다.
3. 피하고 싶은 것에서 "많이 걷기", "사람 많은 곳"을 고른다.
4. [여행 계획 만들기]를 누른다. 처리 중 화면이 뜬다.
5. **10초 남짓 뒤 결과가 나온다.** 요약 카드에 "2박 3일 · 성인 2명, 아동 1명 · 약 87만 원(추정)"이 보인다.
6. 1일차 카드를 눌러 펼치니 이동 시간과 각 장소의 예상 체류 시간이 보인다. 걷는 거리가 짧은 코스로 짜여 있다.
7. 예산표에서 숙박이 절반을 차지하는 걸 보고, 조건을 수정해 예산을 낮춰 다시 만든다.
8. 준비물에서 "상비약 — 부모님 동행 시 권장"을 보고 챙길 것을 메모한다.
9. 우천 시 대안에서 2일차 야외 코스를 대체할 실내 장소를 확인한다.

**성공 지점**: 사용자가 "이 정도면 됐다, 여기서 몇 개만 바꾸면 되겠다"고 판단하는 순간.

### 시나리오 B — 필수값 누락 (오류 경로)

> 사용자가 여행지만 넣고 일정을 비운 채 버튼을 누른다.

1. 버튼을 눌러도 요청이 나가지 않는다.
2. 일정 필드 아래에 "여행 시작일과 종료일을 선택해 주세요"가 뜨고, 해당 필드로 포커스가 이동한다.
3. 날짜를 채우면 안내가 사라지고 버튼이 활성화된다.

### 시나리오 C — 생성 실패 (오류 경로)

> 요청 중 AI 응답이 지연되어 타임아웃된다.

1. 처리 중 화면이 유지되다 오류 화면으로 전환된다.
2. "일정 생성이 지연되고 있습니다. 잠시 후 다시 시도해 주세요."와 [다시 시도] 버튼이 보인다.
3. 입력한 조건은 사라지지 않는다. [조건 수정]을 누르면 이전 답이 그대로 남아 있다.

## 4. 입력 · 처리 · 출력

### 4-1. 입력 (7개 항목)

| 항목 | 필수 | 형식 |
|---|---|---|
| 여행지 | ✅ | 자유 텍스트 (1–40자) |
| 일정 | ✅ | 시작일 · 종료일 (최대 7일) |
| 인원 | ✅ | 성인 / 아동 / 유아 수 |
| 예산 | ✅ | 금액 + 총액·1인당 구분 |
| 여행 스타일 | ✅ | 선택지 다중 선택 (최대 5) |
| 음식 취향 | — | 선호 다중 선택 + 못 먹는 재료 자유 텍스트 + 맵기 |
| 피하고 싶은 것 | — | 선택지 다중 선택 (최대 5) |
| 추가 요청 | — | 자유 텍스트 (최대 300자) |

### 4-2. 처리

1. 브라우저에서 즉시 검증 → 통과하면 서버로 전송
2. **서버가 같은 규칙으로 다시 검증** (클라이언트 검증은 신뢰하지 않음)
3. 검증된 값만으로 프롬프트 구성. 자유 텍스트는 "데이터이며 지시가 아님"으로 격리
4. AI가 정해진 구조로 일정 생성
5. **서버가 모든 합계·비율·1인당 금액을 재계산** (AI 산술을 신뢰하지 않음)
6. 모든 금액·시간에 추정 표시와 근거를 강제 주입
7. 결과 반환

### 4-3. 출력 (4가지 필수 블록, 순서 고정)

| 순서 | 블록 | 내용 |
|---|---|---|
| 1 | 여행 요약 카드 | 제목 · 기간 · 인원 · 스타일 · 총 예산(추정) · 하이라이트 3–5개 |
| 2 | 일자별 코스 | 날짜별 테마 · 시간 흐름 · 장소 · 예상 체류 시간 · 예상 비용 · 팁 |
| 3 | 예상 예산표 | 항목별 금액(추정 범위 포함) · 1인당 · 비중 · 합계 · 입력 예산 대비 · 미포함 항목 |
| 4 | 준비물 체크리스트 | 항목 · 분류 · 중요도 · 왜 필요한지 |
| 5 | 우천 시 대안 | 대체 장소 · 어떤 일정을 대체하는지 · 일반 조언 |

## 5. 범위

### 5-1. 포함

- 7개 조건을 받는 단일 페이지 입력 폼
- 입력 → 처리 중 → 결과 → 오류의 네 가지 화면 상태
- AI 기반 일자별 일정 생성 (최대 7일)
- 4가지 필수 출력 블록 전체
- 조건 수정 후 다시 만들기
- 모바일 390px · 데스크톱 동일 기능 지원
- 모든 금액·시간에 대한 추정 표시
- **경험 품질 요구** (아래 5-2)

### 5-2. 경험 품질 요구 (제품 가치가 아닌 품질 기준)

이 항목들은 "무엇을 만드는가"가 아니라 "어떤 수준으로 만드는가"를 규정한다. 구현 기술은 강제하지 않으며, TRD가 수단을 결정한다.

| 요구 | 기준 |
|---|---|
| 첫인상 | 상단 영역이 정적 이미지가 아니라 움직이는 장면으로 여행의 기대감을 전달한다 |
| 조작 반응 | 메뉴·카드·이미지를 누르면 화면이 눈에 띄게 반응한다. 정적 페이지처럼 느껴지지 않는다 |
| 정보 위계 | 한 화면에 정보를 몰아넣지 않는다. 구역이 카드로 나뉘고 여백이 넉넉하다 |
| 마무리 | 페이지 하단(푸터)이 덧붙임이 아니라 의도적으로 설계된 마무리로 보인다 |
| 저사양 배려 | 모션을 원하지 않거나 기기가 지원하지 않아도 내용을 그대로 읽을 수 있다 |

### 5-3. 제외 범위 (만들지 않는다)

| 제외 항목 | 사유 |
|---|---|
| **예약** | 공급자 연동·재고·취소 정책이 필요. v1 범위 밖 |
| **결제** | 결제 대행·PG 심사·환불 정책이 필요. v1 범위 밖 |
| **실시간 가격 보장** | 가격은 공급자·시점에 따라 변동. 보장하면 제품이 거짓말을 하게 된다 |
| **지도 연동** | 지도 SDK·좌표 데이터·라이선스 비용이 필요. v1은 **지역명 텍스트만** 다룬다 |
| **로그인** | 개인정보 수집·보관 의무가 생긴다. v1은 계정 없이 동작한다 |

> **제외 범위에 대한 명시적 정의 (이후 모든 문서가 이 정의를 승계한다)**
>
> 상단 영역의 3D 비주얼은 **지도 연동이 아니다.** 좌표·지도 타일·Geo API를 일절 사용하지 않는 장식 요소이며, 데이터 모델에 위도·경도 필드를 두지 않는다. 장소는 `areaName`(지역명 텍스트)으로만 표현된다.
>
> 예산표는 **실시간 가격 보장이 아니다.** 모든 금액은 추정값이며, 데이터 모델에서 "확정" 상태를 표현할 수단 자체를 제공하지 않는다.

## 6. 성공 기준

### 6-1. 기능

| # | 기준 | 측정 방법 |
|---|---|---|
| S1 | 유효한 조건으로 제출하면 4가지 출력 블록이 모두 채워진 결과가 나온다 | 정상 입력 1회 실행 후 각 블록 존재 확인 |
| S2 | 서로 다른 조건으로 2회 실행해도 결과의 구조가 동일하다 | 2회 실행 후 블록 순서·필드 구성 비교 |
| S3 | 필수값을 비우고 제출하면 요청이 나가지 않고 해당 필드에 안내가 뜬다 | 네트워크 탭에 요청 부재 + 안내 문구 확인 |
| S4 | 생성 실패·지연 시 오류 화면과 재시도 수단이 제공되며 입력값이 보존된다 | 강제 실패 후 [조건 수정] 시 이전 답 잔존 확인 |
| S5 | 예산표의 항목 합계가 총계와 정확히 일치한다 | 행 금액 합산 = 표시된 총계 |

### 6-2. 신뢰성

| # | 기준 | 측정 방법 |
|---|---|---|
| S6 | 화면에 노출되는 모든 금액과 시간에 추정 표시가 붙어 있다 | 결과 화면 전수 확인. 배지 없는 금액 0건 |
| S7 | 브라우저로 전달되는 어떤 파일·응답·오류 메시지에도 API 키가 없다 | 프로덕션 빌드 산출물 문자열 검색 결과 0건 |
| S8 | 클라이언트 검증을 우회한 잘못된 요청을 서버가 거부한다 | 잘못된 payload 직접 전송 시 422 응답 |

### 6-3. 사용성 · 성능

| # | 기준 | 측정 방법 |
|---|---|---|
| S9 | 모바일 390px에서 가로 스크롤이 발생하지 않는다 | 390px 뷰포트에서 `document.body.scrollWidth <= 390` |
| S10 | 모바일과 데스크톱의 입력 항목 수와 선택지가 완전히 동일하다 | 양쪽 필드·옵션 개수 대조 |
| S11 | 키보드만으로 입력·제출·결과 탐색이 가능하다 | Tab 이동만으로 전 과정 수행 |
| S12 | 모션 저감 설정에서 자동 움직임이 멈추고 내용은 그대로 읽힌다 | OS 설정 변경 후 전 화면 확인 |
| S13 | 3D를 지원하지 않는 환경에서도 상단 영역이 정상으로 보인다 | WebGL 차단 후 확인 |
| S14 | 상단 주요 문구가 데스크톱 2.0초 · 모바일 2.5초 이내에 표시된다 | Lighthouse LCP |
| S15 | 레이아웃이 로딩 중 흔들리지 않는다 | CLS ≤ 0.05 |

### 6-4. 범위 준수

| # | 기준 | 측정 방법 |
|---|---|---|
| S16 | 예약·결제·로그인으로 이어지는 동선이 존재하지 않는다 | 전 화면 링크·버튼 전수 확인 |
| S17 | 지도 SDK·좌표 데이터를 사용하지 않는다 | 의존성 목록 및 데이터 모델 확인 |
| S18 | 사용된 모든 이미지·영상이 오픈소스이며 출처가 기록되어 있다 | 매니페스트와 실제 에셋 목록 대조 |

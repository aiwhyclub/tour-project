## 1. 배포 전 설정

### 1-1. `vercel.json`

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "framework": "nextjs",
  "regions": ["icn1"]
}
```

`vercel.ts`(신형)가 아니라 `vercel.json` 을 택했다. `vercel.ts` 는 `@vercel/config`
의존성을 요구하는데, 두 줄짜리 정적 설정을 위해 의존성을 하나 더 들이는 것은
이 저장소의 공급망 규율(`minimumReleaseAge` 를 우회하지 않는다)과 어긋난다.

`regions: ["icn1"]` 의 근거 — 사용자는 한국어 사용자이고 `/api/plan` 은
Gemini 응답을 기다리는 동안 함수가 살아 있는 유일한 동적 라우트다.
기본 리전(`iad1`, 워싱턴)이면 왕복이 한 번 더 태평양을 건넌다.

### 1-2. 환경변수

`GEMINI_API_KEY` 를 **넣지 않았다.** 키가 없으면 `lib/env.ts` 가 `PLAN_SOURCE=auto`
를 `mock` 으로 해석하므로 전체 화면이 목업 데이터로 동작한다. 배포 파이프라인과
런타임을 먼저 검증하고 실연동은 나중에 붙인다.

> R2 관점에서 이 선택은 공짜가 아니라 이득이다 — 지금 이 배포에는 유출될 키가 없다.

## 2. 빌드 로그 — 확인한 것

### 2-1. pnpm 버전 (배포 전 최대 위험)

`pnpm-lock.yaml` 은 lockfileVersion `9.0` 이지만 내용에는 pnpm 12 전용 필드가 들어 있다:

```
settings: autoInstallPeers: true
overrides:  react: 19.2.8 / react-dom: 19.2.8 / postcss: '>=8.5.23'
packageManagerDependencies: pnpm 12.3.4
```

이 `overrides` 는 `pnpm-workspace.yaml` 에서 온 것이다(pnpm 12 는 `package.json` 의
`pnpm` 필드를 무시한다). **pnpm 9 는 override 를 `package.json` 에서 읽으므로**,
Vercel 이 lockfileVersion 만 보고 pnpm 9 를 골랐다면 `--frozen-lockfile` 설치가
불일치로 실패했을 것이다.

실제 로그:

```
Detected `pnpm-lock.yaml` version 9 generated by pnpm@12.x from package.json#packageManager pnpm@12.3.4
```

Vercel 은 lockfileVersion 이 아니라 **`package.json#packageManager` 를 읽었다.**
Phase 1 에서 추가한 `"packageManager": "pnpm@12.3.4"` 한 줄이 이 위험을 막았다.

### 2-2. 공급망 정책

```
✓ Lockfile passes supply-chain policies (389 entries in 6.7s)
```

`minimumReleaseAge` 정책이 빌드 환경에서도 적용됐고 389개 항목이 전부 통과했다.
로컬에서 정책을 우회하지 않은 결정이 여기서 회수된다 — 우회했다면 이 검증이
프로덕션에서 처음 실패했을 것이다.

### 2-3. 번들

```
Route (app)                                 Size  First Load JS
┌ ○ /                                    93.9 kB         197 kB
├ ○ /_not-found                            125 B         103 kB
├ ƒ /api/plan                              125 B         103 kB
└ ○ /icon.svg                                0 B            0 B
+ First Load JS shared by all             103 kB
```

로컬 `pnpm build` 와 **동일한 197 kB**. 2f 의 코드 분리(Flip · ResultView · ErrorView)가
Vercel 빌드에서도 같게 동작한다.

라우트 4개의 정적/동적 구분도 의도대로다 — `/api/plan` 만 `ƒ`(동적)이고
나머지는 `○`(프리렌더)다. 서버리스 함수는 3개 생성됐다(`lambdaRuntimeStats: {"nodejs":3}`).

### 2-4. 남은 경고 1건

```
Warning: Detected "engines": { "node": ">=20" } in your `package.json` that will
automatically upgrade when a new major Node.js Version is released.
```

수정하지 않았다. CI 는 Node 22 로 고정돼 있고(`.github/workflows/ci.yml`),
`engines` 를 좁히면 로컬 개발 환경까지 묶인다. 다만 **Node 메이저가 올라가면
빌드 런타임이 말없이 따라 올라간다**는 사실은 기록해 둔다.

## 3. 라이브 검증

전부 배포된 URL 에 직접 요청했다.

### 3-1. 정적 자산 · 헤더

| 확인 | 명령 | 결과 |
|---|---|---|
| 폰트 자체 호스팅 | `curl -sI .../fonts/PretendardVariable.subset.woff2` | `200` · `content-type: font/woff2` · **310,368 B** |
| 폰트 캐시 정책 | 같은 응답 | `cache-control: public, max-age=31536000, immutable` ✅ |
| `X-Powered-By` 제거 | `curl -sI .../ \| grep -ci x-powered-by` | **0** ✅ |
| 리전 | `x-vercel-id` | `icn1::…` ✅ |
| 캐시 | `x-vercel-cache` | `HIT` (프리렌더된 `/`) |

`next.config.ts` 의 `/fonts/*` immutable 헤더는 로컬에서 폰트 파일이 없던 시절
죽은 설정이었다. **2a 에서 폰트를 벤더링한 뒤 이 배포에서 처음으로 실제 효력을 확인했다.**

### 3-2. 서버 검증 (R3)

잘못된 형태로 POST:

```bash
curl -X POST .../api/plan -H 'Content-Type: application/json' \
  -d '{"destination":"제주도", …, "party":{…}, "budget":{"amount":900000,"currency":"KRW"}}'
```

```json
{"ok":false,"error":{"code":"VALIDATION_FAILED","message":"입력한 조건을 다시 확인해 주세요.",
"retryable":false,"fields":{"partySize":"인원을 입력해 주세요.","budget.scope":"예산 기준을 선택해 주세요."}},
"meta":{"requestId":"req_l92gtkq6mtxrlaxu","latencyMs":8,"source":"mock"}}
```

- HTTP **422**, 8ms
- 필드 오류가 **한국어**, 영문 Zod 메시지 유출 0건
- 스택·파일 경로 0건
- `source: "mock"` — 키 미설정이 의도대로 해석됐다

### 3-3. 정상 경로 · 불변식

올바른 요청(3일, 성인2·아동1, 90만원, 스타일 3개) → **200**, 1.42초, 19,490 B.

| 불변식 | 검증 | 결과 |

| R8 총계 | Σ 예산행 = 총계 | `675,000 = 675,000` ✅ |
| R8 범위 | Σ rangeLow = total.rangeLow | `573,750 = 573,750` ✅ |
| R8 일자 소계 | Σ items.cost = daySubtotal | 3일차 전부 일치 (124,000 / 191,000 / 94,000) ✅ |
| 비중 합 | Σ sharePercent | **100.0** (정확히) ✅ |

| R5 | 좌표 패턴 (`\d{2}\.\d{4,},\s*\d{2,3}\.\d{4,}`) | **0건** ✅ |
| S16 | `https?://` 링크 | **0건** ✅ |
| S16 | 전화번호 패턴 | **0건** ✅ |
| 면책 | disclaimers 개수 | **4** (degraded 아님) ✅ |
| 구조 | days / checklist / rainy | 3 / 10 / 3 ✅ |

`generation.model` 은 `mock-fixture`, `degraded: false`.

### 3-4. SSR 렌더

```html
<h1 class="text-display-responsive text-white">조건만 넣으면,<br/>일자별 계획이 나옵니다</h1>
```

47,840 B 의 HTML 에 h1 이 그대로 들어 있다. 폰트 preload 링크도 확인했다 —
**LCP 요소가 서버에서 오고, 그 글꼴이 preload 된다**는 전제가 배포본에서도 참이다.

## 4. 접근 통제 — 프리뷰/프로덕션 어긋남과 정정

### 4-1. 무슨 일이 있었나

사용자는 **"프리뷰만 먼저"** 를 선택했다. 그런데 `main` 이 프로덕션 브랜치이고
Git 연동 프로젝트 생성 시 `main` 커밋으로 첫 배포가 걸리므로, 배포가
**`target: "production"`** 으로 올라갔다.

배포 직후 상태:

| URL | 상태 |
|---|---|
| `tour-project-lac.vercel.app` (프로덕션 별칭) | **200 — 공개** |
| `tour-project-creator-47ed9835.vercel.app` | 302 → SSO |
| `tour-project-git-main-…vercel.app` | 302 → SSO |
| `tour-project-qrubytppb-…vercel.app` (배포 고유) | 302 → SSO |

원인은 기본 보호 설정이었다:

```json
"ssoProtection": { "enabled": true, "deploymentType": "all_except_custom_domains" }
```

Vercel 의 "Standard Protection" 은 **프로덕션 도메인만 열어 둔다.** 즉
프리뷰성 URL 은 전부 막혀 있었지만 정작 프로덕션 별칭 하나가 공개돼 있었다.

### 4-2. 정정

사용자 의도("아직 공개하지 않는다")에 맞춰 보호 범위를 전체로 넓혔다:

```json
"ssoProtection": { "enabled": true, "deploymentType": "all" }
```

정정 후 실측:

| URL | 상태 |
|---|---|
| `tour-project-lac.vercel.app` | **302 → SSO** |
| `tour-project-qrubytppb-…vercel.app` | **302 → SSO** |
| `POST /api/plan` | **401** |

이제 팀 구성원만 접근할 수 있다. 실질적으로 **전체가 프리뷰**다.

> 공개로 전환하려면 이 설정 한 곳만 되돌리면 된다
> (`deploymentType` 을 `all_except_custom_domains` 또는 `preview` 로).
> 되돌리기 쉬운 방향으로만 움직였으므로 배포·빌드 결과는 그대로 살아 있다.

### 4-3. 남은 노출 면

| 항목 | 상태 |
|---|---|
| 커스텀 도메인 | 없음 |
| `GEMINI_API_KEY` | Vercel 에 미설정 — 유출될 키 자체가 없다 |
| 검색 색인 | SSO 게이트가 `x-robots-tag: noindex` 를 붙인다 |
| 실사용자 | 0 — 신규 프로젝트이고 공유한 적 없다 |

## 5. 레이트리밋의 실제 유효 범위 — 정정된 서술

`lib/rate-limit.ts` 의 기존 주석은 "실제 방어선은 배포 단계의 Vercel Firewall 규칙"
이라고 적혀 있었다. **이 배포 환경에서는 사실이 아니다.**

- 팀 플랜은 **Hobby** 이고, Firewall 의 rate limit 규칙은 유료 기능이다.
- 따라서 지금 존재하는 유일한 방어선은 프로세스 메모리 버킷이다.
- Fluid Compute 는 인스턴스를 재사용하므로 버킷이 **어느 정도** 지속되지만,
  인스턴스가 여러 개로 늘어나면 각자 자기 버킷을 갖는다 → **전역 한도가 아니다.**

전역 한도로 가는 길은 두 가지뿐이고 둘 다 지금은 택하지 않았다:

1. **Vercel Firewall rate limit 규칙** — 유료 플랜 필요
2. **외부 저장소**(Redis/KV 등) — TRD 8장 SEC13 의 "저장소 의존성 0개"와 충돌

주석을 이 사실대로 고쳤다(`1171c2f`). 현재 상태에서 레이트리밋은
**단일 인스턴스 내 남용 억제**이지 분산 환경의 보증이 아니다.

> 지금은 SSO 로 전체가 막혀 있어 실질 노출이 0이다. 공개 전환 시점에
> 이 항목을 다시 판단해야 한다.

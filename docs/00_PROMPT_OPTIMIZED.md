# 여행 큐레이션 — 최적화 프롬프트 (확정본)

> 원본 12단계 프롬프트 체인에 4가지 추가 조건(GSAP+Three.js · Hero 모션그래픽 ·
> refero/tasteskill 계열 디자인 · 오픈소스 에셋)과 footer.design 요구를 통합하고,
> 조건 간 충돌 3건과 프로덕션 누락 5건을 해소한 버전이다.

---

## A. 원본 대비 변경 요약

### A-1. 해소한 충돌

| # | 충돌 | 해소 규칙 |
|---|---|---|
| C1 | 조건2 참고 링크(Adobe Stock·Envato = 유료 구독, Behance = 타인 저작물) ↔ 조건4 "오픈소스만" | 해당 링크는 **스타일 연구 전용**. 에셋 취득 금지. 실제 에셋은 Pexels/Pixabay 자체 호스팅 + GSAP/Three.js 코드로 작성한 모션 |
| C2 | PRD 제외범위 "지도 연동 없음" ↔ 조건1 Three.js 3D | 3D는 **좌표·지도 타일·Geo API를 쓰지 않는 장식 비주얼**로 정의. 데이터 모델에 좌표 필드 자체를 두지 않음(`areaName` 텍스트만) |
| C3 | "실시간 가격·운영시간 보장 금지" ↔ 필수 산출물 "예상 예산표" | 면책을 **타입 레벨에서 강제**. `Confidence` 유니온에 `'confirmed'` 멤버가 존재하지 않아 "확정"을 표현하는 것이 불가능. 모든 금액·시간은 추정 객체 |

### A-2. 보완한 누락

| # | 항목 | 내용 |
|---|---|---|
| M1 | 모션 접근성 | `prefers-reduced-motion: reduce` 시 pin·scrub·영상·Canvas 전면 해제 |
| M2 | 성능 예산 | 3D 청크 초기 번들 제외, LCP/INP/CLS 목표, 영상 용량 상한을 수치로 명시 |
| M3 | 에셋 출처 관리 | `public/assets-manifest.json`(기계 판독) + `docs/asset-license.md`(사람 판독) 이중 기록 |
| M4 | 서버측 입력 검증 | FRD 작성 시점부터 "클라이언트 검증은 UX 보조, 서버 검증이 유일한 권위" 명시 |
| M5 | 실패 폴백 | 영상 autoplay 거부 / WebGL 미지원 / WebGL 컨텍스트 손실 / 모델 타임아웃 각각의 사용자 대면 경로 정의 |
| M6 | Footer 설계 | footer.design 분류 체계(Typographic·Grid·Animated·Bright)를 근거로 푸터를 독립 설계 대상으로 승격 |

## B. 공통 컨텍스트 (모든 단계에 선행 적용 — 매 단계 재기술하지 않는다)

```
[제품] 여행 큐레이션 — 여행 조건을 입력하면 일자별 계획이 나오는 한국어 웹 도구.

[입력 항목] 여행지 · 일정 · 인원 · 예산 · 여행 스타일 · 음식 취향 · 피하고 싶은 것
[필수 출력] 일자별 코스 · 예상 예산표 · 준비물 체크리스트 · 우천 시 대안
[화면 상태] 입력 → 처리 중 → 결과 → 오류 (단일 페이지 흐름)
[결과 섹션 순서] 여행 요약 카드 → 일자별 코스 → 예산표 → 준비물 → 우천 시 대안

[제외 범위 — 절대 만들지 않는다]
  예약 · 결제 · 실시간 가격 보장 · 지도 연동 · 로그인

[불변 규칙]
  R1. 확인되지 않은 실시간 가격·운영시간을 사실로 보장하지 않는다.
      금액·시간은 데이터 모델에서 추정 객체(confidence + basis)로만 표현되며,
      UI는 그 값을 읽어 배지를 렌더한다. 정적 푸터 면책 문구로 대체하지 않는다.
      타입에 '확정(confirmed)' 상태를 두지 않아 위반을 컴파일 단계에서 막는다.
  R2. API 키는 서버 환경변수에서만 읽는다. 브라우저 번들·네트워크 응답·
      오류 메시지·로그 어디에도 키가 나타나지 않는다. 키가 닿는 파일은 한 곳뿐이다.
  R3. 클라이언트 입력 검증은 UX 보조일 뿐이며, 서버측 검증이 유일한 권위다.
      서버는 원본 body를 쓰지 않고 파싱 결과만 사용한다.
  R4. 모바일 390px와 데스크톱의 입력 항목·선택지는 완전히 동일하다. 배치만 다르다.
  R5. 3D는 좌표·지도 타일·Geo API를 사용하지 않는 장식 비주얼이다. 지도 연동이 아니다.
  R6. 모든 이미지·영상은 오픈소스(Pexels/Pixabay)만 사용하고 저장소에 자체 호스팅한다.
      public/assets-manifest.json에 파일·출처 URL·라이선스·저자·수정 여부를 기록한다.
  R7. prefers-reduced-motion: reduce 환경에서는 pin·scrub·자동재생 영상·Canvas를
      전부 해제하고 정적 대체를 제공한다. 콘텐츠는 그대로 읽을 수 있어야 한다.
  R8. 모델이 계산한 합계를 신뢰하지 않는다. 모든 합계·비율·1인당 금액은
      서버에서 라인 아이템으로부터 재계산한다.

[기술 스택] Next.js 15 App Router · TypeScript(strict) · Tailwind CSS v4 · Vercel
            GSAP + ScrollTrigger + Flip + ScrollTo · Three.js (React Three Fiber + drei)
            Google Gemini API (@google/genai) · Zod

[디자인 방향]
  인상: 여행을 앞둔 설렘 + 정보를 한눈에 훑는 정돈됨
  색상: 바다색 계열 파랑 기준색, 강조색은 정확히 하나만 추가, 배경은 흰색에 가깝게
  글꼴: 한글 고딕(Pretendard). 제목과 본문의 크기 차이를 뚜렷하게
  레이아웃: 구역을 카드로 분할, 여백 넉넉히. 한 화면에 정보를 몰아넣지 않는다
  레퍼런스 어휘: refero "Mercury"(차분·신뢰·블루아워) × "Air"(개방·유리질)
  Footer: footer.design 분류 기준 Typographic × Grid × Animated × Bright 조합.
          대형 타이포 스테이트먼트 + 그리드 링크 컬럼 + 스크롤 진입 애니메이션.
          푸터는 페이지의 마무리가 아니라 독립 설계 대상으로 다룬다.

  참고 사이트(스타일 연구 전용 — 에셋 취득·복제 금지):
    tasteskill.dev · refero.design · styles.refero.design · footer.design
    Adobe Stock / Envato / Behance / motionsites.ai / motion.so / raylight.app
    ※ 위 사이트의 에셋은 유료이거나 타인 저작물이다. 모션의 "방향성"만 참고하고
       실제 모션은 GSAP/Three.js 코드로 직접 작성한다.

[성능·접근성 예산]
  3D 렌더러는 초기 번들에서 제외한다 (dynamic import, ssr: false)
  Hero 배경 영상은 모바일에서 로드하지 않고 정적 포스터로 대체한다
  LCP 요소는 Hero의 "텍스트"이지 영상이 아니다
  WebGL 미지원·컨텍스트 손실·영상 재생 거부·모션 저감은 각각 폴백 경로를 갖는다
  키보드만으로 전체 입력·제출·결과 탐색이 가능해야 한다
```

## C. 단계별 프롬프트

### 단계 1 — PRD

```
[Role] 제품 관리자(PM)
[Task] 공통 컨텍스트를 전제로 이 서비스의 PRD를 한 장으로 작성한다.
[Constraint]
  - 제외 범위에 R5(3D는 지도 연동이 아님)를 명시해 이후 문서가 같은 정의를 승계하게 한다
  - 성공 기준은 측정 가능한 문장으로 쓴다
    (예: "모바일 390px에서 가로 스크롤이 발생하지 않는다")
  - GSAP/Three.js 모션은 "제품 가치"가 아니라 "경험 품질 요구"로 분류해
    기술 선택을 강제하지 않는다
[Format] 마크다운 1장.
  문제 / 대상 사용자 / 사용자 시나리오 / 입력·처리·출력 / 범위 / 제외 범위 / 성공 기준
[산출] docs/01_PRD.md
```

### 단계 2 — 디자인 시안

```
[Role] UI 디자이너
[Context] docs/01_PRD.md를 읽고 그 내용을 기준으로 화면을 설계한다.
[Task] 상태별 화면 시안 4벌(입력/처리 중/결과/오류)을 모바일 390px·데스크톱 양쪽으로.
[Constraint — 화면]
  - 입력 화면: 여행 조건 입력 영역 + [여행 계획 만들기] 버튼
  - 결과 화면: 공통 컨텍스트의 섹션 순서를 그대로 따른다
  - 모바일과 데스크톱의 입력 항목·선택지를 동일하게 한다 (R4)
  - 실제처럼 보이는 예시 여행지와 일정을 채운다.
    글자 길이가 실제와 비슷해야 화면이 깨지는지 알 수 있다
[Constraint — 모션]
  - Hero: 영상 배경 / 3D 오브젝트 / 텍스트 레이어의 z-order와
    스크롤 시 각 레이어 거동을 명시한다
  - 카드·메뉴·이미지 클릭 시 동적 반응을 상태로 표현한다
  - 모션 저감·모바일 폴백 시안을 별도로 포함한다
[Constraint — Footer]
  - footer.design 분류(Typographic·Grid·Animated·Bright)에 근거해 푸터를 독립 설계한다
  - 대형 타이포 스테이트먼트 / 그리드 링크 컬럼 / 스크롤 진입 애니메이션 /
    범위 고지(예약·결제·지도·로그인 미제공) / 에셋 출처 표기를 포함한다
[Format] 디자인 사양 문서 + 토큰 정의. design/ 폴더에 저장.
  이 시안은 최종 구현이 아니라 React 컴포넌트로 옮길 기준이다.
[산출] design/*.md
```

### 단계 3 — FRD

```
[Role] 기능 분석가(BA)
[Context] docs/01_PRD.md와 design/ 시안을 읽고 기능을 정의한다.
[Task] 기능 요구사항 문서를 작성한다.
[Constraint]
  - 기능 ID는 F-01부터. 입력 → 처리 중 → 결과 → 오류 화면 순서로 번호를 매긴다
  - 각 기능에 사용자 행동 / 입력값 / 처리 규칙 / 출력값 / 오류 상태 / 완료 조건
  - 입력 검증, 처리 중 표시, 결과 표시, 다시 만들기, 오류 안내를 포함한다
  - 모션·인터랙션도 기능으로 정의한다
    (Hero 모션, 카드 클릭 확장, 스크롤 연동, 푸터 진입 애니메이션,
     모션 저감 폴백, WebGL 미지원 폴백, 영상 재생 거부 폴백)
  - 입력 검증 규칙은 클라이언트·서버 양쪽에 동일 적용됨을 명시한다 (R3)
  - 시안에 PRD에 없는 요소가 있으면 버리지 말고 기능으로 정의한 뒤
    'PRD에 없음'으로 표시한다. 단 PRD 제외 범위 해당 항목은 뺀다
  - PRD와 시안이 다르면 작성 전에 먼저 묻는다
[Format] 세 부분.
  1) 기능 목록 표 — 기능 ID / 기능명 / 해당 화면 / 한 줄 설명
  2) 입력 항목 표 — 항목명 / 필수 여부 / 형식 / 검증 규칙 / 기본값
  3) 기능 상세 — 기능 ID 순서로, 기능마다 여섯 항목을 같은 순서로
[산출] docs/03_FRD.md
```

### 단계 4 — TRD

```
[Role] 소프트웨어 아키텍트
[Context] docs/01_PRD.md, docs/03_FRD.md, design/ 시안을 읽는다.
[Task] 기술 요구사항 문서를 작성한다.
[Constraint]
  - Vercel 배포를 전제로 한 구성을 제안한다
  - Gemini 모델명은 공식 문서에서 현재 사용 가능한 정확한 이름을 확인해 쓴다
  - 구조화 출력으로 JSON 형태를 강제하는 방법을 명시한다.
    Zod 스키마 하나를 (a) Gemini 응답 스키마 생성과 (b) 응답 검증에
    동시에 쓰는 단일 진실원천 구조로 설계한다
  - 모델이 깨진/부분 응답을 냈을 때의 검증·복구·재시도·폴백 사다리를 정의한다
  - 모델 산술을 신뢰하지 않고 합계를 서버에서 재계산하는 지점을 명시한다 (R8)
  - API 키 취급은 R2를 그대로 따른다. 키가 닿는 파일을 한 곳으로 제한한다
  - 서버측 입력 검증 위치와 스키마를 명시한다 (R3)
  - GSAP·R3F가 App Router에서 SSR/하이드레이션을 깨지 않는 경계를 정의한다
    ('use client' 위치, dynamic import ssr:false, 언마운트 정리, 플러그인 등록 지점)
  - 스크롤 모션이 R3F를 구동할 때 프레임마다 React 리렌더가 발생하지 않는 구조를 정한다
  - 의존성 peer 범위를 실제로 확인하고 충돌 가능한 조합을 고정한다
  - 성능 예산을 수치로 적는다 (3D 청크 크기, LCP/INP/CLS, 영상 용량 상한)
  - 선택한 기술의 이유와 포기하는 대안을 짧게 비교한다
  - PRD·시안·FRD가 다르면 작성 전에 먼저 묻는다
[Format] 기술 구성 / 데이터 흐름 / 파일 역할 / 환경변수 / API 요청·응답 구조 /
         Gemini 연동 설계 / 모션 아키텍처 / 보안 원칙 / 성능·접근성 예산 / 대안 비교
[산출] docs/04_TRD.md
```

### 단계 5 — 개발 계획

```
[Role] 개발 리드
[Context] docs/ 문서와 design/ 시안을 읽는다.
[Task] 개발 계획을 세운다.
[Constraint]
  - EPIC은 3개. EPIC 하나가 끝나면 그것만으로 브라우저에서 결과를 확인할 수 있어야 한다
  - EPIC 경계는 "데이터 출처"로 나눈다: 없음 → 목업 → 실연동.
    각 경계에서 교체되는 의존성이 정확히 하나여야 한다
  - STORY 하나에는 한 가지 동작만 담는다
  - 테스트·보안 점검·배포는 EPIC 안에 넣지 않는다. 세 EPIC이 끝난 뒤 따로 한다
  - docs/03_FRD.md에 없는 기능을 STORY로 만들지 않는다
  - 각 EPIC의 완료 조건은 브라우저에서 눈으로 확인 가능한 문장으로 쓴다
[Format] EPIC별로 묶은 표.
  열은 EPIC / STORY ID / 작업 / 기능 ID / 수정할 파일 / 완료 조건.
  표 아래에 EPIC 3개의 완료 기준을 한 줄씩.
[산출] docs/05_개발계획.md
```

### 단계 6~8 — EPIC 1 / 2 / 3 구현

```
[Role] 계획서대로 구현하는 개발자
```
